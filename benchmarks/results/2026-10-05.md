# Initial validation benchmark baseline — 2026-10-05

Measured core revision: **48a7bde8e4fdbb34f85d700597c87d60c24aff69**, with the
new shared benchmark sources in this topic. This precedes the separately planned
binding lifetime and explicit-context changes; re-run comparable workloads after
integration before attributing a difference to those changes.

Pins: SDK **10.0.401**, runtime **.NET 10.0.12**, BenchmarkDotNet **0.15.8**,
ReactiveUI / ReactiveUI.Reactive **26.0.1**, Runic.DynamicData /
Runic.DynamicData.Reactive **10.0.0-runic.5** (released, bootstrap-verified).
Host reported by BenchmarkDotNet: Linux **NixOS 26.11 (Zokor)**, **Intel Core
i9-12900K**, 24 logical / 16 physical cores, x64 RyuJIT x86-64-v3, concurrent
workstation GC. Both flavors use their synchronous immediate scheduler.

Verification completed:

- Separate benchmark solution: Release build with `-warnaserror`, zero warnings
  and errors, including both core ProjectReferences in Release.
- `--list flat`: eight shared workloads discoverable.
- `--smoke --job Dry --filter '*'`: all **eight** workloads executed successfully
  for each flavor at `Count=10`, including setup correctness and cleanup checks.
- `--smoke --job short --filter '*ContextBenchmarks.InvalidMessageRoundTrip*'
  '*RuleBenchmarks.PropertyValidityRoundTrip*'`: **two** warmed measurements per
  flavor, sequential runs. ShortRun: one launch, three warmups, three measured
  iterations. See the [commands](../README.md) for reproduction.

These warmed observations are provisional shared-desktop baselines. Other tasks
were using this host; high-priority scheduling was unavailable (permission
denied), and this was not an idle-machine experiment. The Reactive rule sample
has a very wide confidence interval. There is no evidence here that either
flavor is faster than the other, or that an algorithm has improved.

| Flavor | Workload (`Count=10`) | Mean | Error (99.9% CI half-width) | StdDev | Managed allocation/invocation |
| --- | --- | ---: | ---: | ---: | ---: |
| Primitives | Context invalid-message round trip | 3.584 μs | 0.5837 μs | 0.0320 μs | 10.16 KB |
| Reactive | Context invalid-message round trip | 3.611 μs | 0.6473 μs | 0.0355 μs | 10.16 KB |
| Primitives | Property validity round trip, ten rules | 39.62 μs | 4.978 μs | 0.273 μs | 83.83 KB |
| Reactive | Property validity round trip, ten rules | 42.93 μs | 94.52 μs | 5.181 μs | 84.61 KB |

Each round trip makes **two** changes and includes resulting synchronous
aggregate work. Allocation units are BenchmarkDotNet's KB (**1024 bytes**).
The context measurement includes creation of the controlled component's states
and validation text. The property measurement includes two property changes,
ten independently observing rules, helper updates, and the active aggregate;
it is not comparable to a single controlled-component update.

The full **1/10/100/1000** matrix was not measured. Construction, membership,
add/remove, clear/repopulate, and public invalid-message workloads received Dry
smoke coverage only; their cold-start timings are deliberately omitted from the
performance table. This does not measure UI latency, asynchronous model turns,
bridge delivery, rendering, native allocations, or Native AOT performance.

Follow-up hypothesis: each property change can refresh several rules, each of
which can trigger an aggregate scan and rebuild error text. Allocation and
scaling under rule fan-out are worth measuring at the existing sizes on an idle
host before considering batching or aggregate algorithm changes. This two-case,
ten-rule sample does not establish scaling, identify a bottleneck, or justify
changing core algorithms. Binding construction/replacement/disposal workloads
should follow the verified lifetime fix rather than preserve known incorrect
binding behavior as a baseline. The following smoke record covers their later
addition; the original timing table above remains a measurement of the earlier
core revision.

Local detailed evidence is retained in the topic worktree's ignored
`artifacts/benchmark-baseline/{primitives,reactive}-{dry,short}-fixed/` reports
and adjacent `.log` files. This report preserves the host, pins, completed scope,
measurements, and limits needed after that disposable worktree is removed.
